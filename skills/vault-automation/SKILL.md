# Vault 自動化の作法

この Vault の自動化は、フック8・スクリプト13・コマンド14 まで育っている。
新しく足すときに一番起きやすい事故は「**動いているように見えて実は死んでいる**」で、
実際 2026-07-24〜26 に RSS ジョブが3日間サイレントで落ち続けた。

このスキルの目的は、**毎回パターンを再導出させないこと**。既存の部品を使えば、
下の失敗モードは構造的に踏めなくなる。

## まず読む

- 部品の一覧と設計判断 → Vault の `System/Claude CodeとVault連携運用.md`
- 使う側の視点 → `System/コマンド早見表.md`
- 詳しいコード例と落とし穴 → `references/patterns.md`(**書き始める前に読む**)

## diagnosing-bugs との住み分け

範囲が隣接しているので、どちらの局面か意識する。

- **`diagnosing-bugs`** = 原因が分からないものを**突き止める**。再現→最小化→仮説→計測の手順
- **このスキル** = **作る・直す**ときに型へ沿わせる。既存部品の再利用と、既知の失敗の回避

「フックが発火しない、なぜ?」は前者。「発火するように直す/新しく作る」は後者。
両方が要る場面(原因は分かったが直し方が分からない)では、原因究明は diagnosing-bugs の
手順で進め、**直し方はここの部品に載せ替える**のが噛み合う。

過去の失敗の多くは「原因が分からなかった」のではなく「**そもそも失敗に気づけなかった**」
ことが本体だった。だから作る側で潰すのが効く。

## 過去に実際に踏んだ失敗

新しい自動化を書く前に、この4つに当てはまらないか確認する。全部この Vault で
実際に起きたもので、どれも「気づけなかった」ことが被害の本体だった。

### 1. 成功していないのに成功したことにする

`touch $STAMP` を実行の**前**に置くと、失敗してもスタンプが進む。ガード窓が閉じるので
再試行されず、ログを読まない限り永久に気づけない。RSS が3日間これで死んでいた。

→ **`vault_bg_run` を使う。** 状態を3つに分ける: `-lock`(排他)/ `-stamp`(**成功時のみ**)/
`.vault-failures.jsonl`(失敗記録)。連続3回失敗でサーキットブレーカが開き、成功で自動復帰する。

### 2. 絶対パスで PATH を無効化する

`export PATH=...` した直後に `/usr/bin/python3` と絶対パスで書くと、せっかくの PATH が効かない。
macOS の `/usr/bin/python3` は **3.9.6** なので、`X | None`(PEP 604 = 3.10+)を書いた瞬間に
def 実行時 TypeError で即死する。

→ **`vault_python` を使う。** パスから推測せず、候補に実際にバージョンを聞いて 3.10+ を返す。
あわせて python 側にも `from __future__ import annotations` を入れる(どのインタプリタで
起動されても落ちない二重の防御)。

### 3. 同じ起動処理を2箇所にコピーする

RSS の起動は SessionStart フックと Templater(`.obsidian/plugins/templater-obsidian/data.json`)の
両方にあり、**両方が同じバグを持っていた**。data.json は JSON 内の文字列なので差分が追えず、
修正が片方にしか当たらなかった。しかもコメント曰く Templater が正規トリガーでフックは保険 —
つまり壊れていたのは本命のほう。

→ **起動口は1つにする。** 新しいバックグラウンドジョブは `scripts/vault-bg-run.sh` に
ジョブ名を足し、フックからも Templater からもそれだけを呼ぶ。

### 4. 無条件に通知する

旧 Stop フックは未コミットが1件でもあれば無条件に `decision: block` していた。Vault には
常時20件前後あるので**毎セッション必ず鳴り**、21件が22件になっても文面が変わらない。
人間は3回で読まなくなり、実際 hot.md には6日前の数字が残ったままだった。

→ **`nudge_should_emit` を通す。** 「状態が変わったときだけ喋る」= 閾値超過 かつ
(初回 / N日経過 / 前回値の1.5倍以上に悪化)。通知には**総量の上限**を設ける
(SessionStart は最大3行、Stop は最大1件)。

## 設計するときの判断

### どのフックイベントか

| やりたいこと | イベント | 例 |
|---|---|---|
| セッション開始時に文脈を足す / 溜まりを知らせる | SessionStart | hot-cache, dashboard |
| 条件が揃ったらバックグラウンドで走らせる | SessionStart | rss-lazy, weekly-lazy |
| 危険な操作を発生前に止める・確認する | PreToolUse | git-guard, folder-guard |
| 編集直後に検査する | PostToolUse(`Edit\|Write`) | lint-posttool |
| 終了時にまとめる・促す | Stop | vault-stop |

**launchd は使わない。** Vault(`~/Documents`)を触る launchd ジョブは TCC で全滅する。
これは既に2回踏んでいる。定期実行がほしいときは「SessionStart + トリガー条件 + 冪等性」で
組む(「今日のデイリーノートがあり、今日の RSS がまだ無ければ走らせる」の形)。

### 指標を足すときは 0 を保てるか考える

ダッシュボードの「重大 n」は、常に3件出ている状態だと**何のシグナルにもならない**。
実際 Blog の誤検出3件が6日間そうなっていた。新しい指標を出す前に「平常時 0 になるか」を
確認し、ならないなら誤検出を潰すか、その指標を出すのをやめる。

**そして「入力を全部見ているか」を先に確かめる。** 通知は行動を促すので、誤検出は
そのまま誤った行動になる。例:「未参照の添付」を通知するなら、参照元を数える側が
`.md` しか読んでいないと、`.canvas` や `.base` にだけ貼った画像が未参照に見える
→ **消してよいと言われた画像を消す事故**になる。

指標を足すとき、この順で確認する:

1. その指標の**入力になりうる場所を列挙**したか(`.md` 以外の形式、除外ディレクトリ、
   埋め込み記法のバリエーション)
2. 平常時に **0(または十分小さい値)**に落ち着くか
3. 誤検出したとき、**取り返しがつくか**。つかない側(削除・移動)に倒れるなら、
   閾値を上げるか、通知を「確認して」の語で止める

`vault-lint.py` の `collect()` は非 `.md` を名前だけ集めて中身を読まない、という
制約が実際にある。既存関数を再利用するときは、その関数が**何を見ていないか**も読む。

### 機械が書く領域と人が書く領域を混ぜない

`hot.md` の「最近の変更」は git から導出できるので機械が書き、「進行中のスレッド」は
セッションの意味なので Claude が書く。週次ノートも `vault-weekly:start/end`(python が毎回
上書き)と `vault-weekly:ai:start/end`(AI の判断)を**別ブロック**にしてある。
混ぜると、次回の実行で人の書いたものが消える。

→ マーカーで囲んで冪等に置換する。既存の実装が `vault-weekly.py` と `vault-hot-auto.py` にある。

### 機械が作るファイルがテンプレの器を壊さないか

週次ノートを機械が新規作成したとき、ダイジェストだけ書くとレビューの器(チェックリスト・
7日分の埋め込み)が入らない。**しかもファイルが存在するので、後から Periodic Notes で
開いてもテンプレは適用されない。** 「回っていないものを回す」つもりで「回っているものを壊す」。

→ テンプレの**解決済みの姿**を CLI 側で再現する(`render_weekly_template()` / `/daily` が前例)。

### 判定ロジックを2箇所に書かない

ダッシュボードが lint と同じ数字を出す必要があったとき、シェルアウトして出力を再パースすると
定義がズレる。`vault-lint.py` と `vault-moc-audit.py` は `analyze()`(データを返す)と
`main()`(表示する)に分割してあるので、**importlib でモジュールとして読んで `analyze()` を呼ぶ**
(ハイフン入りファイル名なので通常の import はできない)。

## 検証

**書いたら必ず走らせる。** これは強調しておきたい — `py_compile` も `ast.parse` も
今回のバグを**検出できなかった**。PEP 604 はアノテーション評価時(= def 実行時)に落ちるので、
構文チェックは通ってしまう。

最低限これを確認する:

```bash
# 1. 実際に起動する(--help でよい)。構文チェックでは不十分
/usr/bin/python3 ~/.claude/scripts/vault-<name>.py --help

# 2. Vault 外では何もしないこと(フックはグローバル登録なので必須)
echo '{"cwd":"{{DOTFILES}}"}' | ~/.claude/hooks/vault-<name>.sh

# 3. shellcheck
shellcheck -S warning ~/.claude/hooks/vault-<name>.sh

# 4. 失敗時にスタンプが進まないこと(意図的に失敗させる)
# 5. 通知系なら、同日2回目で黙ること
# 6. ファイルを書くなら、2回実行して重複しないこと(冪等性)と手書き部分が残ること
```

**SessionStart に足すものは速度も測る。** 目安は 0.2 秒未満。重い処理は
stale-while-revalidate(古いキャッシュをそのまま使い、裏で更新)にする
(`vault-status.py` が前例)。

## 仕上げ

1. **allowlist に足す。** 新しいスクリプトを呼ぶなら `~/.claude/settings.json` の
   `permissions.allow` に追加する。許可漏れは SessionStart での**無言の失敗**になり、
   今直している失敗クラスを新規に作ることになる。
   呼び出し形式はシバンに合わせる(依存なしの python3 スクリプトを `uv run` 形式で
   許可しても、実際の呼び出しにマッチせず死にエントリになる)。
2. **状態ファイルを `.gitignore` に足す。** `-lock` / `-stamp` / `.jsonl` / キャッシュ。
3. **取説を更新する。** `System/Claude CodeとVault連携運用.md` の部品表に1行。
   ユーザーから見た使い方が変わるなら `System/コマンド早見表.md` にも。
4. **dotfiles と Vault は別リポジトリ。** 両方コミットする。

## やらないこと

- **ユーザーのノートを勝手に編集・削除・移動しない。** 提案 → 承認 → 実行の順を守る。
  既存のスクリプトは全部これを守っている(lint も moc-audit も読み取り専用)
- **自動コミットしない。** 未コミットを知らせるのはよいが、コミットは本人の判断
- **通知を足すときは同時に上限も足す。** 上限のない通知設計は必ず疲労で死ぬ
